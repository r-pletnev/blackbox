# max_depth proposal

## Контекст

Сейчас `blackbox` снимает артефакты только для той функции, которая явно
задекорирована.

Идея на вырост: поддержать режим вложенного трейсинга, в котором декоратор
собирает артефакты не только для корневой функции, но и для пользовательских
функций, вызванных из нее, на ограниченную глубину.

Это выглядит полезно, но пока отложено как future work.

## Цель

Добавить режим, который работает так, будто вложенные пользовательские функции
были задекорированы отдельно вручную, но без необходимости реально вешать
декоратор на каждую из них.

Артефакты при этом должны сохраняться в том же формате, что и сейчас:

- `input.pkl`
- `output.pkl`
- `meta.json`

Именование директорий и файлов должно быть таким же, как если бы каждая
вложенная функция была задекорирована отдельно.

## Предлагаемый API

```python
@blackbox(max_depth=1)
def foo():
    ...
```

Семантика:

- `max_depth=1` — текущее поведение, только корневая функция
- `max_depth=2` — корневая функция + прямые пользовательские subcall
- `max_depth=3+` — глубже по графу пользовательских вызовов

Рабочая гипотеза:

- `max_depth` должен считать только пользовательские вызовы
- вызовы из stdlib, `site-packages` и внутренностей `blackbox` в глубину не идут

## Что считать пользовательским кодом

Базовая идея: определять это по `frame.f_code.co_filename` во время trace.

Предлагаемый подход:

- по умолчанию автодетектить `project_roots`
- базовый default: `Path.cwd()` в момент вызова корневой функции
- дополнительно ориентироваться на путь файла самой корневой функции
- исключать `.venv`, `site-packages`, stdlib и сам `blackbox`

Параметр `project_roots` можно добавить как override для нестандартных случаев:

- monorepo
- запуск не из корня проекта
- несколько src-root

Но по умолчанию лучше не заставлять пользователя передавать его руками.

## Почему это интересно

- можно снимать цепочку вычислений глубже одной функции
- не нужно вручную декорировать каждый внутренний helper
- существующий формат артефактов и helper-утилиты продолжают работать
- это особенно полезно для локальной отладки сложных сценариев

## Ограничения v1

Если делать это, то сначала только для sync-функций.

Причина не в том, что async невозможно поддержать, а в том, что nested tracing
для async заметно сложнее:

- выполнение идет через event loop и await-points
- стек вызовов живет не так линейно, как в sync-коде
- сложнее корректно связать parent/child вызовы
- больше риск получить нестабильное или трудно объяснимое поведение

Поэтому разумный v1:

- обычный async-декоратор работает как сейчас
- `max_depth > 1` поддерживается только для sync
- async-функции с `max_depth > 1` не должны падать: они пишут
  `RuntimeWarning` и выполняются как `max_depth=1`

## Рекурсия и уникальность артефактов

Рекурсия должна поддерживаться естественно:

- если глубина позволяет, рекурсивные вызовы тоже сохраняются
- если достигнут лимит `max_depth`, более глубокие вложенные вызовы игнорируются

Важно: нельзя полагаться только на timestamp + hash аргументов для уникальности
директории вызова.

Коллизия возможна если:

- вызовы происходят в одну и ту же микросекунду
- аргументы совпадают
- есть рекурсивные или очень быстрые повторные вызовы

Предпочтительное решение:

- добавить session-local sequence number

Пример:

```text
20260426_120102_123456_0007_ab12cd34
```

Где:

- timestamp полезен для чтения
- `0007` — порядковый номер вызова внутри одной trace-session
- hash аргументов остается вспомогательной частью имени

## Нужно ли расширять meta.json

Пока нет уверенности, что стоит добавлять много новых полей.

Реально возможные сценарии использования:

- показать цепочку вызовов в редакторе или UI
- фильтровать артефакты по глубине
- находить parent/child связи между вызовами

Минимально полезные поля, если nested mode когда-нибудь будет реализован:

- `depth`
- `callId`
- `parentCallId`

Позиция на сейчас:

- не добавлять эти поля заранее
- вернуться к этому в момент реальной реализации `max_depth`

## Предварительная реализационная идея

Высокоуровнево это могло бы работать так:

1. Корневой декоратор создает trace-session.
2. Включается trace/profile-механизм.
3. На каждом пользовательском `call` создается внутренний call-context.
4. На `return` или `exception` сохраняются артефакты вызова.
5. Глубина считается только по пользовательским frame.

Технически это ближе к trace-based orchestration, чем к обычному decorator
wrapper на каждой функции.

## Почему откладываем

Идея выглядит сильной и потенциально очень полезной, но сейчас это не
приоритетный этап развития библиотеки.

Причины отложить:

- повышенная сложность реализации
- заметный runtime overhead
- отдельная сложность для async
- нужен аккуратный дизайн фильтрации пользовательского кода
- нужно время на тестирование рекурсии, исключений и nested call graph

Итог:

- кейс признан полезным
- направление зафиксировано
- реализацию откладываем до более зрелого этапа проекта
